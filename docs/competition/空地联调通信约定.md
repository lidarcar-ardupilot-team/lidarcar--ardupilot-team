<a id="purpose"></a>
## 为什么需要这份约定

题面要求无人机、救援车和参赛电脑之间使用无线通信；无人机识别出的二维码信息和坐标也必须能显示到参赛电脑。于是，无线链路不只是“把小车叫醒”，而是空地任务闭环中的可检查接口。

本约定只解决**应用层目标信息**的共同格式。它不替代飞控安全状态、树莓派雷达位姿帧、电机安全逻辑，亦不把任何历史联调结论推广为新设备已经通过。

<a id="links"></a>
## 链路与角色

```text
无人机识别 / 定位
       │  二维码编号 + 目标坐标（无线）
       ├────────────────────────────→ 参赛电脑：显示目标信息与坐标
       └→ 无线 AS32 ───────→ 小车 AS32 ─ UART3 ─→ MSPM0G3507

参赛电脑 ←→ USB-TTL + 另一只 AS32 ←→ 无线链路 ←→ 小车 AS32
```

| 角色 | 责任边界 |
| --- | --- |
| 无人机 | 识别二维码，生成目标编号与坐标，并按协议发送；飞行/投放安全状态另行维护。 |
| 小车 MSPM0G3507 | 解析目标帧，保留飞机原始坐标，完成坐标转换后再触发路径规划、到点和返航。 |
| 参赛电脑 | 显示二维码编号、坐标和调试信息；不承担主控制。 |
| AS32 | 透明无线串口链路。模块地址、信道和空中速率属于链路层；应用帧的 `target_id` **不是** AS32 模块地址。 |

<a id="frame"></a>
## 9 字节目标坐标帧

AS32 按透明串口理解，当前主协议为下列 9 字节帧；不要把早期自定义的 `AA55 len/type/seq/checksum` 方案继续当作主协议。

```text
AA BB target_id qr_id x_hi x_lo y_hi y_lo FF
```

| 字段 | 定义 |
| --- | --- |
| `AA BB` | 帧头。 |
| `target_id` | 应用层目标设备：公共广播 `0x10`、飞控 `0x20`、小车 `0x30`、参赛电脑 `0x40`。 |
| `qr_id` | 目标二维码：A=`0xCA`、B=`0xCB`、C=`0xCC`。 |
| `x_hi x_lo` / `y_hi y_lo` | 有符号 `int16` 大端（高字节在前），单位 `cm`。发给小车时先按飞机相对坐标理解。 |
| `FF` | 帧尾。 |

地面站发给飞控的帧，坐标字段填 `0x00`。A 码公共广播可使用 `AA BB 10 CA FF FB 01 04 FF` 作为解析样例；它只用于核对帧格式，不能替代当前场地坐标标定。

<a id="as32"></a>
## AS32 与 MSPM0G3507 接口

| 项目 | 当前口径 / 边界 |
| --- | --- |
| 小车端串口 | `UART3/openmv`：`PA14 = MCU TX → AS32 RXD`，`PA13 = MCU RX ← AS32 TXD`。名称 `openmv` 只是历史外设名；当前用途是无线 AS32。 |
| 串口配置 | 当前 AS32 实测使用 `115200 8N1`。若 SysConfig 初始生成 `openmv=9600`，固件需明确记录何处、何时改为 `115200`，不能靠默认值猜测。 |
| 模式 | `MD0`、`MD1` 接地时按普通透明传输理解；该状态不做模块参数配置。 |
| `AUX` | 当前未接 MCU；接收/发送逻辑不得依赖 `AUX` 忙闲脚，应以 UART 字节、合法帧与超时管理链路。 |
| 电脑侧接入 | 电脑若通过串口助手与小车无线通信，应使用另一只 AS32 加 USB-TTL；不是把电脑直接接到小车 AS32。 |
| 链路层前提 | 透明模式下，模块地址、信道、空中速率需匹配。若改成定点传输，发送数据还需携带接收方地址和信道前缀；当前 9 字节文档帧不包含该前缀。 |

<a id="coordinates"></a>
## 坐标边界：先转换，再规划

无线帧里的 `x/y` 是飞机坐标系下、以厘米计的二维码中心。小车接收层只输出 `target_raw_flight_frame`；坐标转换层输出 `target_map_frame`。A*、路径跟踪和停车判断只能消费后者。

在坐标轴暂视为平行时，最小转换形式为：

```text
target_map_x = air_origin_map_x_cm + air_sign_x * air_x_cm
target_map_y = air_origin_map_y_cm + air_sign_y * air_y_cm
```

`air_origin_map_*`、正方向符号、是否轴交换，以及二维码中心的实测定义，必须在实际场地确认后版本化记录。未确认前，不能把历史 A/B 坐标常数硬编码为新场地的通用坐标。

### 小车与无人机初始点的 X 向偏移

当前场地记录有一项不能在坐标转换时丢失：**小车初始点相对无人机初始点在 X 方向相差 `80 cm`。** 这是一项场地锚点，不是无线帧新增字段，也不应混入二维码相对坐标。

记录或实现转换时，先把符号写清：

```text
car_start_map_x_cm = air_start_map_x_cm + start_offset_x_cm
abs(start_offset_x_cm) = 80 cm
```

`start_offset_x_cm` 的正负必须跟随当轮地图 `+X` 定义填写；若不同端使用相反 X 轴，应在坐标转换层显式取反，不能只在某一端把 `80` 改成魔法数。每轮联调记录至少同时给出无人机起飞区中心、小车出发区中心、`+X` 朝向和该偏移的符号。

<a id="test"></a>
## 联调与变更规则

1. 三端先在诊断/台架模式确认帧头、帧尾、目标设备、二维码编号、字节序、单位和超时；再允许目标进入小车任务状态机。
2. 测试记录至少包含无人机/小车/电脑版本、两只 AS32 的链路配置、发送原始帧、接收解析结果、坐标转换结果和时间戳。
3. 任意改变帧格式、`target_id`、坐标定义、波特率或 AS32 配置时，同步修改本页、小车与无人机接口记录，并回退到三端仍兼容的版本。
4. 已记录的 A/B 无线联调只覆盖相应的到点、停车、返航和起点停稳条件；C 码及任何新硬件必须单独取得证据。

赛题中的无线评分项及其证据边界，见 [评分与证据矩阵](评分细则与证据对照.md#function)。
