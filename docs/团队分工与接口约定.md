<a id="interface-record"></a>
## 跨模块接口记录

任何会被另一个模块消费的信息，都在**提供方和使用方目录各留一个链接或同一份接口页**。不要只在聊天记录里说明。

```text
接口名称：
提供方 / 使用方：
用途与触发条件：
物理链路或软件通道：
消息字段、单位、坐标系、字节序：
更新率、超时与有效期：
安全失效行为：
版本 / 提交：
台架验证：
实车/飞行验证：
回退方式：
```

没有上述最小字段时，接收方只能把输入视为 `planned` 或诊断数据；不得把它接入电机、飞控解锁、投递或停车等安全决策。

<a id="change-flow"></a>
## 变更与联调顺序

1. **单模块先自证。** 修改人先在自己的目录记录硬件版本、构建版本、最小命令和结果；小车按 [控制工作流](../car/docs/开发流程与测试规范.md) 分层进行。
2. **接口后联调。** 双方核对接口记录中的单位、方向、频率、超时和失败行为，先在诊断/台架模式走通。
3. **硬件在负责人目录核对。** 小车 PCB、线束或供电变动时，更新 [`car/hardware/`](../car/hardware/) 的事实和板测；无人机、视觉硬件同理。不要用软件补偿掩盖未确认的接线。
4. **保存同轮证据。** 联调记录需注明三个端的版本、场地/装配、操作顺序和时间对齐方式。一次成功只覆盖记录中的条件。
5. **再合并。** 代码、接口页和证据链接一起提交；任一方撤回/改接口时，回退到双方仍兼容的提交。
