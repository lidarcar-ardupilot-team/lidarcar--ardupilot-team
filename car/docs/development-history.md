<a id="how-to-use"></a>
## 如何使用这份时间线

1. 想恢复某一阶段的行为，先找到对应 checkpoint，再比对当时的硬件、场地、坐标和日志；**不要**只复制一个速度或距离常量。
2. 想修当前问题，先回到 [开发工作流](workflow.md) 和当前 PCB / `.syscfg` / 实物量测；历史分支只用于提出和排除假设。
3. 想引用“已完成”的结论，仍要看 [视频证据索引](../evidence/20260710-airlink-ab-return/README.md) 与 [资料状态](../../docs/evidence-and-status.md)。分支名只能说明当时保存了什么，不能代替同轮验证。

<a id="decisions"></a>
## 路线为何这样演变

### 1. 从“让车走起来”转为“先确认车在哪里”

早期出现过定位结果与实际地图不一致、回到初始姿态有漂移的情况。后续策略不再把问题归结为单一 PWM 或路径阈值，而是先检查雷达、建图/定位、坐标转换和数据新鲜度。阶段快照中可以看到 Cartographer 方案之后转向 Ubuntu 22.04、ROS 2 Humble 与 `slam_toolbox` 的重建路线；这个选择解释了后续代码中对位姿有效性和返航保护的关注，但不能替代当前机器上的重新部署与测量。

### 2. 从假定禁区转为实测禁区几何

曾经直接假设禁区坐标并对 A* 调参，结果难以判断是规划策略还是输入地图错误。后续开发将禁区坐标和膨胀半径当作应先测量的输入，路径规划才消费这些数据。现有阶段文件中的硬边界、软代价和目标附近奖励，都是这个调整留下的机制痕迹。

### 3. 从到点展示转为完整返航闭环

广西区赛阶段曾将“到达二维码”理解为主要终点；复盘题目后，国赛准备阶段把到目标二维码中心、返航至红色区域中心和停车一起纳入测试。这个修正对应多二维码返航与停车 checkpoint；评分依据仍以 [赛题与评分](../../docs/competition/) 的正式文本为准。

### 4. 从单车测试转为空地接口联调

最后的 A/B 联调不把“收到无线字节”直接当作任务成功，而是依次核对 AS32 透明串口、目标帧、目标编号、坐标转换、路径状态、目标停车与返航。当前的 [通信约定](../../docs/competition/communication-contract.md) 将这些接口边界固定下来；现有 A/B 视频仅作为这一阶段的 `stage-record`。

<a id="boundaries"></a>
## 历史分支与当前仓库的关系

以上锚点来自项目原开发工作区中保存的 checkpoint / archive 分支。它们是本仓库阶段控制文件、视频索引和开发复盘的**追溯来源**，不是这个仓库必须依赖的子模块，也不应把完整历史工作区、构建产物、原始日志或凭据直接复制进来。

本仓库的整理原则是：

- 把可阅读的阶段代码、硬件资料、接口、证据索引和结论边界留在对应模块；
- 把大视频、原始日志、完整历史工程保存在确认过的外部归档位置，并通过文件名、哈希、版本或稳定链接定位；
- 当需要复现旧版本时，从历史锚点恢复到独立工作目录，再按当前 PCB、`.syscfg` 和场地重新走验证流程。
