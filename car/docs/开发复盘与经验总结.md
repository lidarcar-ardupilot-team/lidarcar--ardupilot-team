<a id="conclusion"></a>
## 先说结论

这段过程最值得保留的不是“最后小车能走”，而是几个顺序被反复验证：

```text
先看评分闭环
    → 再实测地图、起点和禁区
        → 再确认雷达位姿是否可信
            → 再让 A* / 路径跟随消费这些输入
                → 最后调速度、转向、停车和联调
```

一开始实际采用过相反顺序：先写路线、调行走参数，再补定位、禁区和返航要求。它能产生很多“车动了”的测试片段，却不能稳定地回答“车在哪里、能否绕开禁区、是否能按赛题回家”。

<a id="deadline"></a>
## 一晚赶交付：先保住材料，再承认联调未完成

网上提交资料前一晚，小车端先临时了解并使用 Cartographer 的雷达结构，准备装车和接入。装配中一块 MSPM0G3507 出现无电压故障而报废；随后改用另一块存储受保护的备用芯片，并额外花时间完成可烧录恢复。那一晚没有完成空地联调。

于是当时做了一个**交付降级**：小车改用蓝牙操作，无人机以手动控制配合，优先完成视频与资料提交。这个决定的价值是把“无法在截止前完成自动联调”与“完全没有可提交材料”区分开；它不是自动空地系统的实现基线。

| 当时做法 | 当时解决的问题 | 后来保留下来的规则 |
| --- | --- | --- |
| 更换故障 MCU，并完成备用芯片的烧录恢复 | 让小车重新具备继续调试的条件。 | 硬件故障、供电、烧录状态要先作为独立检查项；不要把它混进控制算法问题。 |
| 蓝牙 + 无人机手动控制 | 在截止前保留可展示的材料。 | 交付保底路径必须明确标为手动/降级模式，不能写成自动联调已通过。 |
| 当夜未完成联调 | 暴露了时间、硬件和接口同时收敛的风险。 | 截止日前应预留独立的端到端联调窗口，而不是把它压到最后一晚。 |

烧录恢复过程只保留版本、结果、适用芯片和验证记录；不在公开仓库展开存储保护绕过或解锁细节。

<a id="wrong-route"></a>
## 近一周的错误路线：在错误坐标上调车

随后几天，小车尝试过“直接拐弯—走直线—返回起点”的路线。测试代码和参数改动很多，但雷达 / Cartographer 坐标本身并不准确；因此车端其实是在错误的位姿输入上不断调转向和距离。这段近一周的尝试没有形成可复用的最终路线。

真正的问题不是“弯不够圆”或“PWM 不合适”，而是规划和控制缺少可信的世界坐标。只要起点、方向或位姿漂移没有先确认，直线、转弯、到点、返航四件事都会同时失去参照。

**由此留下的规则：** 每次开始调路径或速度前，先保存一份起点、姿态、目标点和雷达位姿的对照；当对照不成立时，停止继续堆叠路线常量，回到定位链路。

<a id="rebuild"></a>
## 重建定位和规划：从 Cartographer 使用到 slam_toolbox

为摆脱旧定位链路的不稳定状态，后续在 Ubuntu 22.04、ROS 2 Humble 环境下重新组织雷达系统，并采用 `slam_toolbox` 作为建图/定位策略。A* 负责在已知地图和禁区输入上生成路线；它不负责修复雷达坐标，也不应替代位姿校验。

重建后效果相对稳定，但仍会出现误差。这是一个重要区分：**“比原来稳定”不等于“坐标已经无条件正确”。** 所以后续的代码和文档保留位姿新鲜度、坐标转换、精停和返航保护等层次，而不是把一次成功路线当成固定常量。

<a id="forbidden-zone"></a>
## 第二次失误：禁区坐标靠猜

定位链路开始可用后，仍然走过一段弯路：没有直接按赛题地图测量禁区坐标，而是先假定禁区位置、调 A* 和小车参数。这又花了数天，且无法判断失败到底来自规划策略还是地图输入本身。

后来改为用雷达和赛题地图实测禁区坐标。这一步才让“避免触碰禁区”的要求变成可计算的规划输入，也让保护距离、软代价、路径拐角和停车判据有了共同的地图基准。它本应更早执行。

```text
错误顺序：猜禁区 → 调 A* → 调车 → 反复失败
正确顺序：读题图 → 实测禁区/起点/目标 → 固化坐标系 → 调 A* → 调车
```

<a id="score-matrix"></a>
## 最后发现：到点不等于完成题目

禁区输入补齐后，小车开始朝“不碰禁区、能与无人机联调”的方向收敛，区赛现场也完成了对应版本的测试。但当时没有把赛题得分矩阵作为每轮验收清单，注意力偏向“到达二维码”，忽略了小车还需要返回起点（红色区域中心）并停车。

这不是单个代码 bug，而是验收条件遗漏。进入国赛准备后，任务才被补成：收到目标 → 坐标转换 → 规划避障 → 到二维码中心停车 → 返航 → 起点区域中心停车。后续多二维码、返航停车和空地联调的 checkpoint，正是为了补上这个闭环。

<a id="methods"></a>
## 留下来的工作方法

| 先问什么 | 再做什么 | 不应直接做什么 |
| --- | --- | --- |
| 这一轮得分/完成判据包含哪些步骤？ | 把到点、避障、返航、停车、通信拆成检查项。 | 只凭“车到了目标”宣布任务完成。 |
| 地图坐标、起点和禁区是否已实测？ | 固化坐标系、偏移和障碍边界，再让规划消费。 | 用估算禁区坐标反复调 A*。 |
| 雷达位姿是否与实物一致且足够新鲜？ | 先记录和核对位姿，再调路径跟随。 | 在明显漂移的坐标上继续调 PWM。 |
| 自动联调是否还来得及完成？ | 明确自动、诊断、手动保底三种状态及其材料边界。 | 把蓝牙/手动展示包装为自动联调。 |
| 硬件与烧录链路是否健康？ | 单独完成供电、MCU、烧录、串口自检。 | 把硬件异常误判为算法调参问题。 |

这些规则与 [开发脉络与版本锚点](开发历程与版本记录.md) 互补：时间线回答“什么时候发生”，本页回答“为什么后来要这样做”。

<a id="boundaries"></a>
## 这份复盘的边界

- 文中“成功”“稳定”都只描述当时的阶段观察，不替代当前 PCB、固件、场地或新机体的验证。
- 小车模块维护底盘、雷达、规划和车端安全；飞控、视觉模型和投递决策分别由其负责人目录维护。
- 当前可公开的 A/B 联调材料仍以 [视频证据索引](../evidence/20260710-airlink-ab-return/README.md) 和 [资料状态页](../../docs/项目资料与验证状态.md) 为准。
- 新一轮复现应从题图、地图量测、硬件版本、固件哈希和原始日志重新开始，而不是复制本页中的路线或参数。
