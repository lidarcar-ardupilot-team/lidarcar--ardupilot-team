## 小车在任务闭环中的位置

```text
无人机识别目标并发送：二维码编号 + 飞机坐标
                              │ AS32 透明串口
                              ▼
小车接收 → 保存原始坐标 → 转换到地图坐标 → A* 规划 / 禁区约束
                                                   │
                                                   ▼
                                      路径跟随 → 二维码中心停车 → 返航停车
```

1. 无线帧中的 `x/y` 先按**飞机坐标系**理解；接收层只能输出原始目标。
2. 坐标转换层生成地图坐标后，规划、路径跟随和停车判断才可消费该目标。
3. 雷达位姿、编码器、姿态和电机保护属于车端安全与执行链路；无线消息不能直接替代这些判断。
4. 三端协议、AS32 接线与坐标边界以 [空地通信约定](../docs/competition/communication-contract.md) 为准；赛题的目标中心、返航区和禁区判据以 [赛题与评分](../docs/competition/) 为准。

## 历史任务启动口径

阶段快照中的按键路线为：`PB7` 启动 A 码、`PB25` 启动 B 码、`PB0` 启动 C 码。这是历史 `empty.c` 的任务入口记录，并非新工程可以直接复制的 PinMux 配置；新板应先完成 [引脚与 SysConfig 验证](docs/mspm0g3507-sysconfig-validation.md)。

本仓库目前只归档 A/B 路线的联调视频。C 码曾属于后续返航方案的开发范围，但没有与当前材料同轮的视频、日志和版本记录，因此仍需独立验证。

## 从历史中保留的工程结论

- **定位问题先回到定位链路。** 早期雷达建图/定位效果不稳定时，先重建并验证定位链路，再讨论路径和速度；不要用控制参数掩盖坐标漂移。
- **禁区先量，再规划。** 禁区和边界的地图几何必须实测并版本化；用假设坐标反复调 A*，很难区分规划问题与输入错误。
- **返回起点是完整任务的一部分。** 到目标二维码中心停车并不代表任务结束；返航区中心、停车和无人机返航应一起按赛题判据核对。
- **联调先验证接口，再上场地。** 先在诊断/台架模式核对帧、单位、字节序、超时与坐标转换，再让目标进入底盘任务状态机。
- **保留可退回的节点。** 每次有可复现改善时保存 checkpoint、视频/日志索引和版本信息；具体时间线见 [开发脉络与版本锚点](docs/development-history.md)。

## 下一次改动的最小记录

每次修改控制、引脚、路线、停车或联调行为，至少在对应模块留下：

```text
目标与赛题判据：
硬件 / PCB / 固件版本：
本轮唯一改动：
输入、坐标与输出执行器：
最小验证命令或操作步骤：
原始日志、照片、视频或哈希：
观测结果、停止条件与回退提交：
```

推荐按 [开发工作流](docs/workflow.md) 的“硬件与 PinMux → 日志 → 位姿与坐标 → 规划与禁区 → 速度执行 → 串联验收”逐层推进。阶段控制文件仍是单文件快照；恢复工程时应把协议、日志、规划、速度环与硬件驱动拆成接口明确的模块。
